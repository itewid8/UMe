# Проектная документация: Приложение "CouplePlan" (MVP)

## 1. Vision & Scope (Видение и границы проекта)

### 1.1. Видение продукта
Мобильное приложение для молодых пар, объединяющее планирование поездок, вишлисты, задачи и совместный календарь в едином пространстве. Продукт устраняет хаос в чатах и заметках, добавляя элемент игры и романтики через режим "Сюрприз".

### 1.2. Целевая аудитория
*   Молодые пары (18–35 лет), живущие вместе или на расстоянии.
*   Пользователи, активно планирующие совместный досуг и путешествия.

### 1.3. Границы MVP (Что входит)
*   **Платформы:** iOS, Android (кроссплатформенная разработка).
*   **Авторизация:** Регистрация, вход, привязка пары по коду/ссылке.
*   **Модули:**
    *   Совместный календарь.
    *   Поездки (карточки, чек-листы, файлы).
    *   Задачи (назначение, статусы).
    *   Вишлист (ссылки, цены, статус).
    *   **Режим "Сюрприз"** (создание, таймер, скрытие контента).
    *   **Шаблоны** (базовая библиотека + сохранение своих + отправка идей).
*   **Уведомления:** Push о новых событиях, напоминания, разблокировка сюрприза.
*   **Офлайн-режим:** Чтение данных, кэширование изменений.

### 1.4. Исключения из MVP (Что отложено)
*   Веб-версия и версия для планшетов (адаптив под планшеты будет, но отдельной версии нет).
*   Финансовый трекинг и бюджеты.
*   Интеграции со сторонними сервисами (авиабилеты, карты).
*   Маркетплейс пользовательских шаблонов (только отправка идей админу).
*   Геймификация (ачивки, уровни).

## 2.5. Acceptance Criteria (Критерии приемки)

### Эпик: Онбординг и Профиль

**US-01: Регистрация через Email/Apple/Google**
- **Given:** Пользователь открыл экран регистрации
- **When:** Пользователь вводит корректный email и пароль ИЛИ нажимает кнопку Apple/Google ИЛИ успешно проходит OAuth
- **Then:** Создаётся аккаунт в системе, пользователь перенаправляется на экран онбординга, генерируется JWT-токен
- **And:** При вводе уже существующего email показывается ошибка «Этот email уже зарегистрирован»
- **And:** Пароль должен соответствовать требованиям (мин. 8 символов, 1 цифра, 1 буква)

**US-02: Отправка приглашения партнеру**
- **Given:** Пользователь авторизован и не имеет активной пары
- **When:** Пользователь нажимает «Пригласить партнера» и выбирает способ (ссылка/код)
- **Then:** Генерируется уникальный код приглашения (6 символов) ИЛИ deeplink-ссылка
- **And:** Код действителен в течение 7 дней
- **And:** Один код может быть использован только один раз

**US-03: Принятие приглашения и синхронизация**
- **Given:** Пользователь получил код/ссылку от партнера
- **When:** Пользователь вводит корректный код ИЛИ переходит по ссылке И завершает регистрацию
- **Then:** Создаётся запись в таблице `Pairs`, оба пользователя получают `pair_id`
- **And:** Происходит начальная синхронизация данных (пустые списки на старте)
- **And:** При вводе неверного кода показывается ошибка «Неверный код приглашения»
- **And:** При попытке принять приглашение пользователем, у которого уже есть пара, показывается ошибка

**US-04: Настройка профиля**
- **Given:** Пользователь авторизован
- **When:** Пользователь загружает фото, меняет имя, переключает уведомления
- **Then:** Данные сохраняются в профиле пользователя
- **And:** Фото сжимается до макс. 500KB перед загрузкой
- **And:** Изменения видны партнеру в течение 5 секунд (через WebSocket)

---

### Эпик: Календарь и События

**US-05: Создание события в общем календаре**
- **Given:** Пользователь имеет активную пару
- **When:** Пользователь создаёт событие с title, start_time, end_time
- **Then:** Событие сохраняется в БД с `pair_id` создателя
- **And:** Партнёр получает событие через WebSocket в реальном времени
- **And:** При end_time < start_time показывается ошибка «Время окончания должно быть позже начала»

**US-06: Push-уведомление о событии**
- **Given:** Событие создано с reminder_time (за X минут/часов)
- **When:** Наступает время напоминания
- **Then:** Оба партнера получают push-уведомление с заголовком и описанием события
- **And:** При клике на уведомление приложение открывается на экране календаря
- **And:** Если у пользователя отключены push в настройках ОС, уведомление не отправляется (ошибки нет)

**US-07: Экспорт в системный календарь (Low Priority)**
- **Given:** Пользователь имеет событие в приложении
- **When:** Пользователь нажимает «Экспортировать в календарь»
- **Then:** Событие добавляется в системный календарь устройства (iOS Calendar / Google Calendar)
- **And:** При изменении события в приложении оно НЕ обновляется в системном календаре (односторонний экспорт)

---

### Эпик: Поездки

**US-08: Создание карточки поездки**
- **Given:** Пользователь имеет активную пару
- **When:** Пользователь заполняет title, location, start_date, end_date и нажимает «Создать»
- **Then:** Создаётся запись в таблице `Trips` с `pair_id`
- **And:** Поездка отображается в списке поездок и на календаре
- **And:** При end_date < start_date показывается ошибка

**US-09: Добавление чек-листа к поездке**
- **Given:** Поездка создана
- **When:** Пользователь добавляет элементы чек-листа (текст, assigned_to)
- **Then:** Элементы сохраняются в таблице `ChecklistItems` с привязкой к `trip_id`
- **And:** Партнёр видит новые элементы в реальном времени
- **And:** Можно назначить исполнителя (себя, партнера, null)

**US-10: Прикрепление файлов к поездке**
- **Given:** Поездка существует
- **When:** Пользователь загружает файл (PDF, JPG, PNG) размером до 10MB
- **Then:** Файл загружается в S3-хранилище, ссылка сохраняется в БД
- **And:** Партнёр может скачать файл по ссылке
- **And:** При размере файла > 10MB показывается ошибка «Файл слишком большой»
- **And:** Поддерживаемые форматы: .pdf, .jpg, .jpeg, .png

**US-11: Использование шаблона чек-листа**
- **Given:** Пользователь создаёт чек-лист для поездки
- **When:** Пользователь выбирает шаблон из библиотеки (например, «Сборы в аэропорт»)
- **Then:** Элементы шаблона копируются в чек-лист поездки
- **And:** Пользователь может редактировать скопированные элементы (удалять, добавлять свои)
- **And:** Оригинал шаблона не изменяется

---

### Эпик: Задачи и Вишлист

**US-12: Создание задачи и назначение исполнителя**
- **Given:** Пользователь имеет активную пару
- **When:** Пользователь создаёт задачу с text, due_date, assigned_to
- **Then:** Задача сохраняется в БД, статус = «pending»
- **And:** Назначенный исполнитель получает push-уведомление (если включено)
- **And:** При выполнении задачи (is_done = true) задача помечается выполненной у обоих партнеров

**US-13: Добавление товара в вишлист**
- **Given:** Пользователь имеет активную пару
- **When:** Пользователь добавляет товар с title, link, price, is_secret
- **Then:** Товар сохраняется в таблице `Wishlist` с `added_by` = ID создателя
- **And:** Если is_secret = true, цена скрыта от партнера (показывается «???»)
- **And:** Партнёр видит товар в списке сразу

**US-14: Отметка товара как «Куплено»**
- **Given:** Товар существует в вишлисте
- **When:** Пользователь нажимает «Куплено» и (опционально) указывает bought_by
- **Then:** Поле `bought_by` заполняется, цена скрывается от партнера (если не была скрыта)
- **And:** Товар перемещается в конец списка или в раздел «Куплено»
- **And:** Создатель вишлиста НЕ получает уведомление о покупке (сохранение интриги)

---

### Эпик: Режим «Сюрприз» (Critical)

**US-15: Создание сюрприза**
- **Given:** Пользователь имеет активную пару
- **When:** Пользователь создаёт сюрприз с content (text/media), recipient_id, reveal_at
- **Then:** Сюрприз сохраняется в БД со статусом `pending`
- **And:** Content НЕ передаётся на клиент получателя до наступления reveal_at
- **And:** Получатель получает push-уведомление «Вам готовится сюрприз!» (без деталей)
- **And:** При reveal_at <= current_time показывается ошибка «Дата раскрытия должна быть в будущем»

**US-16: Отображение факта сюрприза и таймера**
- **Given:** Сюрприз создан со статусом `pending`
- **When:** Получатель открывает ленту сюрпризов
- **Then:** Отображается карточка с заголовком, иконкой и таймером обратного отсчёта
- **And:** Таймер обновляется в реальном времени (каждую секунду)
- **And:** Поле `content` в API-ответе = `null`

**US-17: Автоматическое раскрытие сюрприза**
- **Given:** Сюрприз существует со статусом `pending`
- **When:** Наступает `reveal_at` (серверное время)
- **Then:** Статус сюрприза меняется на `revealed`, поле `content` становится доступным
- **And:** Получатель получает push-уведомление «Сюрприз готов! Откройте приложение»
- **And:** При запросе `/surprises/{id}` бэкенд возвращает полный контент
- **And:** На клиенте проигрывается анимация раскрытия (fade-in/shatter effect)

**US-18: Безопасность контента сюрприза (Critical)**
- **Given:** Сюрприз создан со статусом `pending` и reveal_at в будущем
- **When:** Получатель (или злоумышленник) делает прямой запрос к API `/surprises/{id}` ДО наступления reveal_at
- **Then:** Бэкенд возвращает HTTP 200 с полем `content` = `null`
- **And:** В логах бэкенда нет утечки контента
- **And:** В кэше приложения (SQLite/Hive) контент не сохраняется
- **And:** Даже при наличии глубокой ссылки на сюрприз контент не отображается
- **And:** При вскрытии трафика (Charles/Proxy) контент не виден

---

### Эпик: Шаблоны

**US-19: Выбор шаблона из библиотеки**
- **Given:** Пользователь создаёт чек-лист или поездку
- **When:** Пользователь открывает библиотеку шаблонов и выбирает шаблон
- **Then:** Элементы шаблона применяются к текущему чек-листу
- **And:** Системные шаблоны (is_system = true) доступны всем пользователям
- **And:** Шаблоны категоризированы (trip, wedding, home)

**US-20: Сохранение своего чек-листа как шаблона (Medium Priority)**
- **Given:** Пользователь имеет чек-лист с элементами
- **When:** Пользователь нажимает «Сохранить как шаблон» и вводит название
- **Then:** Чек-лист сохраняется в таблице `Templates` с is_system = false
- **And:** Шаблон доступен только этой паре (не глобально)
- **And:** Можно использовать шаблон повторно в будущих поездках

**US-21: Отправка идеи шаблона (Low Priority)**
- **Given:** Пользователь хочет предложить шаблон
- **When:** Пользователь заполняет форму (название, описание, элементы) и отправляет
- **Then:** Данные сохраняются в таблице `TemplateSuggestions`
- **And:** Администратор получает уведомление (email/admin panel)
- **And:** Пользователь видит сообщение «Спасибо! Мы рассмотрим вашу идею»

## 2.5. Non-Functional Requirements (NFR)

### 2.5.1. Производительность (Performance)
| Метрика | Целевое значение (P95) | Примечание |
|---|---|---|
| **Cold Start Time** | < 2.0 сек | Время от тапа по иконке до отображения первого кадра UI |
| **Time to Interactive** | < 3.0 сек | Время до полной отзывчивости интерфейса |
| **API Response Time** | < 500 мс | Для основных операций (загрузка плана, синхронизация) |
| **Frame Rate** | ≥ 55 FPS | Плавность анимаций и скролла |
| **Размер приложения (Install Size)** | < 50 MB (iOS), < 100 MB (Android) | Без учета кэша данных пользователя |

### 2.5.2. Надежность (Reliability)
| Метрика | Целевое значение | Примечание |
|---|---|---|
| **Crash-Free Users** | > 99.5% | Доля пользователей без крашей за сессию |
| **ANR Rate (Android)** | < 0.1% | App Not Responding события |
| **API Availability** | > 99.0% | Доступность бэкенда для успешных запросов |
| **Data Loss Prevention** | 0% потерь | Гарантия сохранения данных при краше или обрыве сети |

### 2.5.3. Безопасность (Security)
- **Аутентификация:** Использование JWT токенов с коротким временем жизни (access token) и refresh token в secure storage (Keychain/Keystore).
- **Хранение данных:** Чувствительные данные (токены, email) хранятся только в зашифрованном виде. Локальная БД (Hive/SQLite) может быть зашифрована при необходимости.
- **Сеть:** Все соединения строго через HTTPS (TLS 1.2+). Certificate pinning (опционально для MVP, но желательно).
- **Приватность:** Данные пользователя не передаются третьим лицам без явного согласия.

### 2.5.4. Энергопотребление и Ресурсы
- Фоновая синхронизация не должна разряжать батарею более чем на 5% в сутки при активном использовании.
- Минимизация использования GPS (только при создании событий с геолокацией).

## 3. Техническая архитектура

### 3.1. Технологический стек
*   **Mobile (Frontend):** Flutter (язык Dart).
    *   *Обоснование:* Единая кодовая база для iOS/Android, высокая производительность рендеринга (Skia/Impeller), отличная поддержка кастомного дизайна и анимаций (важно для "Сюрприза").
*   **Backend:** Python (FastAPI) или Node.js (NestJS).
    *   *Рекомендация:* Python (FastAPI) — быстрая разработка, удобная работа с данными, типизация.
*   **База данных:** PostgreSQL (основные данные) + Redis (кэш, сессии).
*   **Хранилище файлов:** S3-compatible storage (MinIO или облачное решение AWS S3 / Yandex Cloud Object Storage).
*   **Real-time:** WebSockets (для мгновенной синхронизации изменений между партнерами).
*   **Push-уведомления:** Firebase Cloud Messaging (FCM) + APNs (через Firebase).

### 3.2. Схема данных (ERD - упрощенно)

**Users**
*   `id` (UUID)
*   `email`, `password_hash`
*   `name`, `avatar_url`
*   `pair_id` (UUID, FK -> Pairs.id, nullable)

**Pairs**
*   `id` (UUID)
*   `user_1_id`, `user_2_id`
*   `created_at`
*   `status` (active, archived, broken)

**Events (Календарь)**
*   `id`
*   `pair_id`
*   `title`, `description`
*   `start_time`, `end_time`
*   `type` (calendar, trip, surprise_reveal)

**Trips (Поездки)**
*   `id`

## 4. API Specification (Основные эндпоинты)

### Auth & Pair
*   `POST /auth/register` — Регистрация.
*   `POST /auth/login` — Вход.
*   `POST /pair/invite` — Генерация кода приглашения.
*   `POST /pair/accept` — Принятие приглашения (код).

### Common Data
*   `GET /sync` — Полная синхронизация данных пары (получение всех сущностей).
*   `WS /ws` — WebSocket канал для realtime обновлений.

### Trips & Checklists
*   `POST /trips` — Создание поездки.
*   `POST /trips/{id}/checklist` — Добавление чек-листа.
*   `POST /templates/apply` — Применение шаблона к чек-листу.
*   `PATCH /checklist/items/{id}` — Обновление статуса элемента.

### Surprises
*   `POST /surprises` — Создание сюрприза.
    *   *Body:* `{ recipient_id, content, reveal_at }`
*   `GET /surprises` — Список сюрпризов (для получателя: без поля `content`, если `reveal_at > now`).
*   `GET /surprises/{id}` — Детали (бэкенд проверяет время и возвращает контент или заглушку).

### Templates
*   `GET /templates` — Список доступных системных шаблонов.
*   `POST /templates/suggest` — Отправка идеи шаблона админу.
*   `POST /checklists/{id}/save-as-template` — Сохранение своего списка (локально/в пару).

## 5. Риски и План миграции

### 5.1. Технические риски
1.  **Синхронизация офлайн/онлайн:** Конфликты при одновременном редактировании списков.
    *   *Решение:* Last-write-wins стратегия для простых полей, мердж для списков (операционные трансформации или CRDT в будущем).
2.  **Безопасность "Сюрприза":** Риск утечки через API или кэш.
    *   *Решение:* Строгая проверка на бэкенде (`if now < reveal_at return null content`). Не передавать зашифрованный контент на клиент до срока.

### 5.2. Продуктовые риски
1.  **Эффект "одного пользователя":** Если партнер не регистрируется, приложение бесполезно.
    *   *Митигация:* Режим "Соло" (черновики), который конвертируется в общий при приглашении.
2.  **Сценарий разрыва:**
    *   *Логика:* При разрыве (кнопка "Разорвать пару") данные `Trips`, `Wishlist` дублируются обоим пользователям как личные архивы. Активные `Surprises` аннулируются или передаются получателю немедленно (на усмотрение создателя).

## 8. Testing Strategy (Стратегия тестирования)

Качество MVP обеспечивается многоуровневой стратегией тестирования. Цель — достичь баланса между скоростью разработки и стабильностью продукта.

### 8.1. Уровни тестирования (Test Pyramid)

| Уровень | Что тестируем | Инструменты | Покрытие (Target) |
|---|---|---|---|
| **Unit Tests** | Бизнес-логика, модели данных, маппинг API, валидация форм, логика синхронизации. | `flutter_test`, `mockito`, `fake_async` | > 80% бизнес-логики (особенно модуль "Сюрпризы" и офлайн-синхронизация). |
| **Widget Tests** | Отдельные виджеты (карточки событий, кнопки, поля ввода), реакция UI на изменения состояния. | `flutter_test`, `golden tests` (для критичных экранов) | Ключевые компоненты UI (Card, Button, Input fields, List items). |
| **Integration Tests** | Потоки внутри приложения (Login → Dashboard → Create Event), работа с локальной БД, моки API. | `integration_test`, `patrol` (опционально) | Критические User Journeys (Happy Path + основные ошибки). |
| **E2E Tests** | Полные сценарии на реальном эмуляторе/устройстве с бэкендом (staging). | `integration_test` (real device farm) | Smoke-тесты перед каждым релизом (Регистрация, Создание пары, Пуш-уведомление). |

### 8.2. Device Matrix & Поддерживаемые платформы

### 8.3. CI/CD Pipeline для тестов

Автоматизация встроена в процесс разработки через GitHub Actions / GitLab CI:

1.  **Pre-commit (локально):** `flutter analyze`, форматирование.
2.  **Pull Request:**
    - Запуск всех Unit и Widget тестов.
    - Сборка приложения (build check).
    - *Блокировка мержа при падении тестов.*
3.  **Nightly Build (develop branch):**
    - Запуск Integration тестов на Firebase Test Lab (или аналоге).
    - Сборка Debug-версии для QA.
4.  **Release Candidate:**
    - Полный прогон E2E smoke-тестов.
    - Генерация отчета о покрытии кода.

### 8.4. Ручное тестирование (QA)

Перед каждым релизом в Store проводится ручное тестирование по чек-листам:

**Чек-лист регрессии (Smoke):**
- [ ] Регистрация и вход (Email + Social).
- [ ] Отправка приглашения партнеру и принятие его.
- [ ] Создание события в календаре.
- [ ] Создание "Сюрприза" и проверка скрытия контента до времени.
- [ ] Работа офлайн-режима (включение авиарежима → действия → включение сети → синхронизация).
- [ ] Получение Push-уведомления.
- [ ] Выход из аккаунта.

**Специфические проверки:**
- Поворот экрана (Portrait/Landscape) — если поддерживается.
- Работа приложения при низком уровне батареи (Power Saving Mode).
- Прерывание работы звонком или сворачиванием приложения во время сохранения данных.

### 8.5. Мониторинг качества (Post-Release)

Для оперативного выявления проблем после публикации используются инструменты мониторинга:

- **Crash Reporting:** Firebase Crashlytics.
  - *Цель:* 0 известных крашей с влиянием >1% пользователей перед новым релизом.
  - *Алерты:* Уведомление в Slack при росте crash-free users < 99%.
- **Performance Monitoring:** Firebase Performance.
  - *Трекинг:* Время холодного старта, длительность HTTP-запросов, скорость отрисовки экранов.
- **Analytics:** События ошибок (например, `api_error_500`, `sync_failed`) для анализа частоты проблем у пользователей.
